# Goal

Connect incremental code changes to open implementation plans so agents and
humans can see which plans, batches, gates, and architecture boundaries are
affected before continuing work.

# Non-goals

Do not silently reopen plans, rewrite plan status, remove stale evidence, add
file watchers, call an LLM, or implement rollback. Plan state changes remain
explicit canonical workflow operations.

# Validation

Run the tests named in the testing contract. Each batch must pass its blocking
gates before completion. Run full regression on batches that change update,
CLI, MCP, doctor, or cross-module parsing behavior.

# Testing strategy

Each implementation batch proves its behavior with focused tests first, then
uses CLI smoke and full regression where a public surface changed. Tests use
temporary project fixtures, bounded assertions, and stable JSON fields.

# Execution notes

Implement one batch at a time. Stop after validation and record the result.
Keep impact logic independent of Typer and MCP. Only CLI, MCP, and service map
user input to the core engine. Cap graph depth, candidates, evidence, warnings,
and output size. Sort deterministic results. Treat malformed plans as warnings.
Never mutate an authoritative Markdown plan as a side effect of impact
reporting.

# Engineering requirements

Keep plan impact logic tool-agnostic in `codeatlas.plan_impact`. Use stable
error codes, repo-relative POSIX paths, bounded traversal, and sorted output.
`direct` means an explicit file or symbol match. `indirect` means a bounded
caller/callee relationship. `possible` is heuristic, scored, and never blocking
by itself. Only `approved`, `executing`, and `blocked` plans are open for new
impact work. `done` plans may be reported for stale evidence, but are not new
impact targets.

# Quality gates

unit-tests, cli-smoke, and regression-tests are blocking. A failed, timed out,
unbound, stale, or missing gate cannot complete a batch.
