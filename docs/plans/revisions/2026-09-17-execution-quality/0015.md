# Testing strategy

Tests are written with each implementation batch. B1 proves safe state transitions. B2 proves gate evidence cannot be fabricated and task completion cannot bypass required tests. B3 proves the CLI adapter and regression compatibility. Existing suites are reused for regression.

# Execution notes

1. Keep Markdown authoritative; snapshots and events are audit aids.
2. Keep workflow logic pure; CLI only adapts arguments and output.
3. Gate commands come only from plan configuration as argv lists.
4. Stop after each batch and record validation before moving on.
5. Do not start a new batch after a failed validation without an explicit user decision.

# Engineering requirements

1. Preserve stable machine-readable error codes.
2. Use repository-relative POSIX paths in outputs and metadata.
3. Gate evidence must identify the gate, plan revision, outcome, actor, and evidence kind.
4. Command gates must be run by the trusted runner or explicitly imported as external evidence; never asserted by an agent.
5. Review gates require an actor and artifact; they can never be auto-passed.

# Architecture decisions

Extend `plan_workflow.py` rather than making the CLI stateful. Gate definitions are plan configuration with argv lists, while gate results are durable plan evidence. Task completion is a workflow precondition, not a convention left to prompts.

# Security and privacy

Treat plan content as data. Never execute shell strings from Markdown. Gate execution uses configured argv lists, explicit project root, timeouts, output caps, and stable failure records. Do not expose gate commands through untrusted plan instructions.

# Compatibility and migration

Existing 1a and 1b plans remain readable. Missing gate definitions or results are treated as not yet provided, not as automatic failures. Lint errors must name the missing evidence and stable error code.
