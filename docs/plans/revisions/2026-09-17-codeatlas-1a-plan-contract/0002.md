# Goal

Deliver `1a-plan-contract`: a local, offline, tool-agnostic Markdown plan parser/linter plus the first four plan CLI commands (`new`, `show`, `status`, `lint`), so later workflow PRs can build on a stable plan artifact instead of prose.

# Non-goals

- Do not implement approval, revision conflict detection, task/batch transitions, gates, or rollback.
- Do not add SQLite plan projection tables in this PR.
- Do not implement `plan context`, `plan impact`, MCP tools, or semantic retrieval.
- Do not couple plan semantics to Codex, Cursor, or any specific agent.
- Do not migrate the two large existing roadmap documents in this PR.

# Current understanding

The repository already has a service-oriented CLI, SQLite indexing, context VM, history, and doctor checks. It has no `src/codeatlas/plans.py`, no `plan` command group, and no plan tables in `.codeatlas/state.db`. Therefore, `1a` can add a pure plan layer and CLI adapter without touching the index.

# Assumptions

1. YAML is already a project dependency, so `safe_load` may be used.
2. Existing plans in `docs/plans/` are design/roadmap documents; PR 1a may treat missing or legacy frontmatter as lint warnings rather than breaking existing behavior.
3. The first command surface is intentionally only `new`, `show`, `status`, and `lint`.

# Validation

1. `python -m pytest tests/test_plan_engine.py` passes.
2. `python -m pytest` passes with existing behavior unchanged.
3. `.venv/Scripts/codeatlas.exe plan lint` exits 0 when the plan is valid and exits non-zero with stable errors for an invalid fixture.
4. `.venv/Scripts/codeatlas.exe plan new smoke-plan --json` creates a valid plan under a temporary root.
5. `.venv/Scripts/codeatlas.exe plan show <id> --view summary --json` returns a bounded object with status, profile, next batch, and warnings.
6. `.venv/Scripts/codeatlas.exe doctor` passes because PR 1a must not regress existing invariants.

# Testing strategy

The frontmatter `testing.tests` contract is authoritative. The body adds the same intent in human-readable form:

- T-001 through T-006 prove parser and lint behavior before any CLI is added.
- T-007 proves bounded status output does not depend on dumping plan bodies.
- T-008 proves the CLI can create and render a valid plan.
- T-009 reuses existing storage/context/MCP tests to protect current behavior.
- T-010 keeps the shipped template aligned with the parser and linter contract.

No migration test is required because this PR does not alter the SQLite schema. No security-specific test is required because plan content is treated as data and no command is executed by the parser.

# Engineering requirements

1. Plan parsing and linting belong in `plans.py`; the CLI only adapts output and exit codes.
2. Paths inside plan metadata are repo-relative POSIX paths.
3. YAML parsing uses safe loading only.
4. JSON output is deterministic: keys sorted, no timestamps except fields present in the plan.
5. Errors are structured, not localized prose.
6. The parser must have bounded input size and actionable diagnostics.
7. Before each batch, review whether the implementation structure is mainstream.
8. Prefer pure core logic plus thin adapters.
9. Use stable machine-readable error codes instead of prose-only errors.
10. Keep paths repo-relative POSIX internally.
11. Use isolated repo-local test temp directories; avoid host Temp dependencies.
12. Disable pytest cache when required by the local environment.
13. Clean test artifact directories after each test run.
14. Never commit local test artifacts.
15. Stop after validation failures, analyze, present options, and wait for the user's decision.

# Architecture decisions

Keep PR 1a as a pure artifact contract before adding persistence. SQLite projection is intentionally deferred to `1b`, because status/lint can operate from files and adding tables now would create migration surface before the schema stabilizes. CLI remains an adapter over `plans.py`.

# Documentation

1. Add module docstrings explaining the plan artifact contract.
2. Add CLI help text for all four commands.
3. Record the PR sequence in the implementation kickoff section of the v13 roadmap.

# Security and privacy

Treat plan Markdown and YAML as data. Do not execute shell strings, interpolate paths outside the project root, or send content to a network service. Reject oversized plan files with a clear diagnostic.

# Compatibility and migration

Existing plan files must remain readable as ordinary Markdown. PR 1a may warn on legacy documents, but it must not fail `scan`, `update`, `query`, `history`, or `context`. It must work on Windows paths and without an existing SQLite index.
